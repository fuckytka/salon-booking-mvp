# Карта трасування

Ідентифікатори FR1–FR5 відповідають практичній №1. Префікс API — `/api/v1`. Запуск перевірок описаний у README.

| Вимога | Процес та реалізація | API | Контроль |
|---|---|---|---|
| FR1. Доступні послуги та слоти | P1. Каталог і вибір дня у frontend/app.js; backend/core.py, slots() відбирає майбутні відкриті слоти за тривалістю й залишком. | GET /services, GET /slots?service_id=… | T01, T11 і браузерний вибір дня |
| FR2. Створити запис за наявності місця | P3.1–P3.5. Профіль, екран підтвердження, create_booking(). Бронювання та подія разом фіксуються перед відповіддю. | POST /bookings → 201 confirmed, повтор → 200 | T02, T05, T08, T09 |
| FR3. Максимум три активні записи | P3.3 та P3.4. BEGIN IMMEDIATE перед підрахунком усіх confirmed за timeslot_id. UI пропонує інший час. | POST /bookings → 409 slot_unavailable | T06, браузерний конфлікт |
| FR4. Власні записи та скасування | P4. Сесія визначає customer_id. get_booking() і список обмежують вибірку власником; PATCH зберігає cancelled_at. | GET /bookings, GET і PATCH /bookings/{booking_id} → 200 або 404 | T03, T04, T07, T10 |
| FR5. Зайнятість у розкладі | P2. Кабінет працівника використовує той самий підрахунок, який визначає доступність. Блокування перевіряє роль та зайнятість. | GET /schedule, PATCH /schedule/{timeslot_id} → 200, 403 або 409 slot_occupied | T11 |

## Від DFD й ERD до працюючої системи

Первинні редаговані моделі збережено в docs/DFD.drawio і docs/ERD.drawio. Фізична модель міститься в backend/schema.sql. Код застосунку написано за практичними №1–3. Історичних вихідних файлів №4–7 не було. Фактичний контракт і реалізований інтерфейс описують фінальну версію.

| Сховище або потік | Фізична модель і рішення |
|---|---|
| D1, D2 | services і timeslots не мають прямого зв’язку. Обрана послуга має вміститися в часовий інтервал. Спільні слоти створює початкове наповнення; працівник керує доступністю блокуванням. Ручне редагування меж інтервалів залишається за межами версії. |
| D3 | bookings з’єднує user_account, services та timeslots трьома зовнішніми ключами. Кожна батьківська сутність має 0..N записів. Скасування залишає історичний рядок. |
| D4 і P5 | Назву notification_outbox з доповнення №2 уніфіковано з ERD №3 як notifications_outbox. Для кожного bookings існує рівно одна подія booking_confirmed. recipient_id дорівнює customer_id, request_id повторює ключ бронювання. Після commit окремий диспетчер доставляє подію у локальний приймач. Додано attempt_count та стани sent/failed з виправлення №2. T08 і T12 перевіряють обидві межі транзакцій. |
| Авторизація | user_account має рівно одну роль. Допоміжна sessions зберігає хеш токена, строк дії, FK на користувача. У публічній реєстрації доступна роль customer. |
| Фізичні типи | UUID та UTC ISO 8601 зберігаються як TEXT, логічні значення як 0/1, ціни як цілі гривні, JSON як текст. SQLite серіалізує записи через BEGIN IMMEDIATE. Механізм замінює запропоноване у №3 блокування рядка PostgreSQL. |
| Коди результатів | SLOT_FULL у моделі відповідає 409 slot_unavailable, STORAGE_ERROR — 503 storage_error. Повторне скасування повертає те саме представлення cancelled зі збереженим cancelled_at. Помилки у JSON мають форму error.code і, для поля, error.field. UI перекладає технічні значення. |

## Нефункціональні вимоги

NFR2 та NFR3 перевіряються оновленням сторінки з чинною сесією й T10. Для NFR1 браузерний тест вимірює p95 за 30 послідовними локальними GET /slots. Ця вибірка характеризує час API на демобазі. Для a11y-first клавіатурний прохід, фокус, помилки, відновлення та viewport перевіряє tests/browser_checks.py. Значення контрасту та результати запуску наведено у фінальному звіті.
